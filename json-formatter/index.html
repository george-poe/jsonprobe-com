A JSON formatter takes compressed or hand-indented JSON and rewrites it with consistent indentation and line breaks, without changing the data. The same operation is also called a JSON beautifier, a pretty printer, a prettifier and an indenter — five names, one operation, and they are interchangeable in every tool you will find.

      
What separates the tools in this category is not the indentation. It is two other things: whether the page survives a large file, and whether a syntax error tells you where it is. This one runs the work in a Web Worker, so the tab keeps responding while a 100 MB file is in flight, and it carries its own parser so the error message names a line and a column instead of quoting a fragment of your text back at you.

      
Nothing is uploaded. There is no upload step to disable: the file is read with FileReader, handed to a worker on the same origin, and the result is written into the page. If you want to check, open the Network panel and format something: besides the ad tag this page loads, the only entries are this page's own five files, and no request carries your document.

What happens when the JSON is broken

    

Two formats of the same failure are handled differently, and the difference matters
on big files.


When a browser's parser can tell you where, it says so. When it can't — and modern
V8 often can't; a message like
Unexpected token '@', … is not valid JSON carries a
snippet instead of a position — a formatter that only relays the engine leaves you
counting commas in a 40,000-line file.


So this page ships its own scanner. It only runs on the failure path: a valid file
never pays for it. On an invalid file it walks the text once, records the first
position where the grammar can't continue, and converts that to line and column.

The last two rows are the ones that make people distrust the tool: a file copied out

delete them; if it only has to work in that editor, leave them.

    
What the format actually allows

    

JSON has two specifications, and they cover different ground:


    

  • RFC 8259 — from IETF. It defines JSON as a data interchange
format, including the requirement that text exchanged between systems be UTF-8. This
is the one engineering teams comply with.
    • 

  • ECMA-404 — from Ecma International. It describes the grammar only,
and says nothing about encoding or transmission.
    • 



Neither one allows comments, trailing commas, single-quoted strings, unquoted keys,
NaN, Infinity, undefined, or a byte-order mark at
the start of a file. There is no number type in the grammar beyond "number": no
integers, no floats, no size limits. That is why everything in the next section can
happen.

    
What formatting can quietly do to your data

    

A formatter is a decoder followed by an encoder, and that round trip is not free.
Six things can change even though the file still parses. All six are pinned by assertions in the harness that ships with this site (test/index.html, run in Chrome 152 / Windows 11):


    

  • Integers outside ±(2^53 − 1) lose digits.
9007199254740993 becomes 9007199254740992. JavaScript has no
64-bit integer type in JSON.parse, so snowflake IDs, Twitter/X IDs and
nanosecond timestamps will be silently rewritten. If your JSON came from a service
that puts IDs in numbers, that is a bug in the service — but the formatter is where
you lose the evidence.
    • 

  • Big numbers get exponent notation. 1e21 comes back as
1e+21, which is valid JSON but not what most databases accept when you
paste it back.
    • 

  • Duplicate keys collapse. {"a":1,"a":2} parses without
error and keeps the last value. The first one disappears with no warning. Keeping the last value is what JavaScript parsers do; RFC 8259 only says names SHOULD be unique and leaves the behaviour unspecified, so another decoder can disagree with you.
    • 

  • -0 becomes 0. Harmless in JSON, but if the value is a sign bit in a protocol, it is no longer the same bytes.
    • 

  • A number too big to represent becomes null. {"n":1e999} comes back as {"n":null} — not an error, not an approximation, and null is a perfectly legal value, so nothing downstream complains.
    • 

  • Integer-looking keys move to the front. {"b":1,"2":2} is stored by JavaScript as {"2":2,"b":1}, so the output is reordered before any sorting option is involved. If anything hashes or signs over key order, this bites whether or not you tick a thing.
    • 



NaN and Infinity are not JSON at all, so a formatter will
reject them — and if you got such a file from JavaScript, note that
JSON.stringify already turned them into null before you ever
saved it. Keys whose value is undefined are dropped entirely.


Practical rule: if exact numeric fidelity matters, quote the numbers as
strings on the way out of your API. Everything else in this list is then
moot.


    
Two spaces, four spaces, or a tab

    

Whitespace carries no meaning in JSON — both grammars ignore it entirely — so this
is purely convention, and the convention has already settled:


    

  • 2 spaces is the default everywhere the default is written down:
JSON.stringify(obj, null, 2) in tutorials, and Prettier's
tabWidth.
    • 

  • 4 spaces shows up in Python shops, because PEP 8 asks for four and
json.dump(obj, f, indent=4) follows it.
    • 

  • Tab is common in Go, where gofmt indents with tabs and
json.MarshalIndent(v, "", "\t") mirrors that.
    • 



Picking either is fine. Mixing them is the actual problem: a repository where some
.json files use 2 spaces and others use 4 turns every edit into a
file-wide reformat, and the diff noise hides the change you came to review.


Sorting keys alphabetically is the other option with a trap in it. It is safe for
objects — key order is not part of JSON's meaning — and this page never touches array
order, because for an array, order is the data.

    
Formatting it without a browser

    

If the file is already on your machine and there is a terminal nearby, you do not
need this page:


# Python, no arguments to remember
python3 -m json.tool in.json

# jq, if it is installed
jq . in.json


// or six lines of your own
const fs = require("fs");
const raw = fs.readFileSync(process.argv[2], "utf8");
fs.writeFileSync(process.argv[3],
  JSON.stringify(JSON.parse(raw), null, 2));


So where does a web page win? Three places. You have the JSON in a clipboard and no
file. You want to look at the structure rather than read it, which is what the tree
view is for. And the file is big enough that cating it into a terminal is
unusable — which is exactly why the worker and the error-position logic exist.


One thing a local python -m json.tool gives you that no browser page
can: an exit code. If you are deciding whether to format in CI, use the CLI.

    
Frequently asked questions

    

      Does my JSON get uploaded anywhere?
      
No. The file is read with FileReader and processed in a Web Worker on the same origin — nothing your document contains reaches a server. Open the Network panel while formatting: besides the ad tag, you will see only this page's own assets — no request this page makes carries your document. There is also nothing to leak afterwards: no save button, no share link, no recent list — no URL anywhere points at what you pasted.

    

    

      How big a file can it handle?
      
There is no cap on how big a file you can paste. The caps that do exist are on what we draw and on how far we hunt for an error, and both are listed here. Measured on Chrome 152 / Windows 11: a 99.9 MB file with 375,833 records formats in 1496 ms, and locating a syntax error in that same size takes 1026 ms. The real limits are your available memory and the browser's maximum string length — measured 7.2× at 100 MB — 721 MB of JS heap sampled right after the run, via a Chrome-only API — because the text, the parsed object and the output all exist at once. Budget eight to ten times to be safe.

    

    

      What is the difference between a formatter and a validator?
      
A validator answers one question — is this legal JSON. A formatter answers another — show it to me readably. They are usually the same code, because you cannot format something you have not parsed, so this page reports syntax errors while formatting and does not need a separate validation step.

    

    

      Why does it say my JSON is invalid when it works fine elsewhere?
      
Almost always one of four things: comments, trailing commas, single-quoted strings, or unquoted keys. Comments and trailing commas are what JSONC allows; single-quoted strings and unquoted keys are JSON5 only, and a jsonc parser such as VS Code's rejects those two. All four are illegal in JSON. Files from VS Code settings, tsconfig.json, .eslintrc.json and devcontainer.json are JSONC.

    

    

      Will formatting change my values?
      
Not the structure, and not strings. It can change numbers: integers outside ±(2^53 − 1) are not guaranteed to survive (9007199254740993 becomes 9007199254740992), large magnitudes switch to 1e+21 notation, and duplicate keys collapse to the last one. If exact numeric fidelity matters, transport those numbers as strings.

    

    

      Can it sort keys alphabetically?
      
Yes — the Sort keys option recurses through every object at every level. Array element order is never changed, because array order is meaningful and reordering it would corrupt the data.

    

    

      Can I use a tab, or a specific indent width?
      
2, 3 and 4 spaces and a tab are all offered. The output is identical apart from the whitespace, so choose whatever your repository already agreed on.

    

    

      Why does this page load so fast?
      
Because it is one HTML file plus four assets, all same-origin, with no web-font requests of any kind. When advertising is on, Google's scripts are the only cross-origin traffic here — that is what pays for the page, and the tool code adds nothing to it. The processing code is one file shared between the page and the worker rather than being duplicated. That is the whole trick — there is nothing clever about the formatting itself.

    

    
How to format JSON

    
    
      
  1. Get the JSON in: Paste it into the input box, drop a .json file on the page, or click to choose one. Nothing leaves the browser.
    2. 
      
  2. Pick the indentation: 2 spaces is the common default. Choose 4 or tab if your project already uses one — output differs only in whitespace.
    3. 
      
  3. Read the error, if there is one: An invalid file gets the exact line and column of the first place the grammar breaks, plus the surrounding text. Trailing commas and comments are the usual culprits.
    4.
